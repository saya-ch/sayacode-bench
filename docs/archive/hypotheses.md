# 开发候选与可检验假设

日期：2026-10-22。以下修改只发生在正式开发与验收模型运行之前；校准题和其同修复组不进入正式集合。候选不保证胜出，选择严格使用开发集预注册规则。

## 观察来源

两道真实资源校准均约十分钟，原生用量完整，没有派发子 Agent。qutebrowser 的参考解复核也失败，因此它主要用于暴露基础设施问题，不能作为提示改善编程能力的依据。

Ansible 校准原环境与全新镜像重判均为 reward=0，镜像与平台一致。正式验证得到 49 通过、10 失败；失败覆盖缓存目录、无效缓存内容、清理和 world-writable 路径。Agent 最终报告的是自建或修改后的测试通过和其他回归表现。这说明“模型报告测试通过”与“外部契约验收通过”必须分开，但目前仍不能将十个失败全都归于某一个提示原因。

逐次结果与补丁／原始证据 SHA 见 `reports/calibration-ansible-v3/`。完整校准轨迹保留在仓库外，没有将隐藏测试内容回传给该次模型。

## 预先限定的两个候选

| 配置 | 单项改变 | 可被否定的假设 | 保持相同 |
| --- | --- | --- | --- |
| diagnostic | 在用户任务后追加需求证据、失败诊断与验证来源区分指导 | 显式核对要求与验证证据可能减少“自建测试通过但接口／生命周期不符”的交付 | 生产 wheel、模型、工具、团队、上下文、摘要和重试 |
| focused | 追加有限范围调查、最小一致修改、避免重复广泛搜索的指导 | 聚焦相关接口和测试可能减少重复调用与调查成本，且不降低外部通过率 | 同上 |

`diagnostic` 在正式模型运行前，依据 Ansible 校准进一步明确“自行编写的检查不能代替外部契约证据”。这项修订没有使用最终任务成绩，也没有把校准要求或答案追加给正式任务。

这些变化是提示配置调优，不是新 Agent 算法，也不独立验证 planning、replan、记忆或多 Agent 的机制收益。只有在任务中实际触发，并另设单因素对照，才能讨论相应机制效果。

## 选择与反例

开发集比较基线和两个候选；成功率相同且用量完整时才使用报告 token 作为第二判据。耗时、错误和未知另报，不用最有利指标临时换胜者。

若两个候选都未改善，则保留基线并完成独立单组最终验收。若某候选在开发胜出，只能说明它适合进入留出集检验；最终区间跨零时不写已经证明提升。真实负结果是研究结论之一。
