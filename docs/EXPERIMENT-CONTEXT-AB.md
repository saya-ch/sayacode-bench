# 实验设计：长上下文压力下的受控 A/B（2026-11-05）

> 状态：**设计定稿；前置条件（P0 3.2.7 重跑）已完成，但 2026-11-07 复盘后需按新口径修订再执行**。执行期间不得修改 `scripts/locked_agents.py`（跑批进程依赖它）。
> 目的：检验「四组 `planned` 落在 **75.0–85.0%** 的窄带，是因为题目太浅（不需要长上下文）而非模型能力趋同」这一假设。
> 预算：本地 ¥0（既是本地网关，也是本地算力）。

## 1. 研究问题

当前证据链：

| 事实 | 数值 | 来源 |
|---|---|---|
| 四个可用 agent 的 planned 通过率 | 78.8 / 85.0 / 77.5 / 75.0（窄带 10.0pp）| `docs/RESULTS-LEDGER.md` §2.1 |
| 题面改动规模（中位） | **2 个文件 / 64 行** | `C:\sb\tmp\explore\task_scale.py` 实测 |
| SAYACODE 只碰 1–2 文件的 trial 占比 | **62%**（49/79） | 同上 |
| 对照：SWE-EVO 平均改动 | 21 文件 | `SWE-bench ProMax` / SWE-EVO 公开数据 |
| 对照：SWE-Bench ProMax 平均改动 | 11.4 文件 / 261.6 行 | 同上 |

**问题**：如果题目根本不需要长上下文，那么"上下文管理、摘要、检索、抗干扰"这些 agent 之间的真实差异就根本没被激活，测出来的只是"基础改代码能力"，而这一层大家都很成熟 → 通过率挤在窄带里，统计上无法区分。

**可检验的预测**：注入大量*无关但看似相关*的上下文后，四个 agent 的通过率应当**下降**，且**下降幅度不同**（退化量 Δ 的组间差异显著）。若注入后仍然挤在窄带、Δ 也没有差异，则说明"上下文压力"不是当前的区分维度，需要换维度（多文件、跨模块、长链路）。

## 2. 设计

### 2.1 自变量

**同一个 task、同一个 verifier、同一个模型**，唯一变量是**指令尾部追加的无关背景材料长度**：

| 变体 | 内容 | 目标上下文占用 |
|---|---|---|
| `clean` | 原始 instruction（与 P0 批次完全一致）| ~5k tokens |
| `noise-30k` | instruction + ≈30k tokens 无关材料 | ~35k（192k 的 18%）|
| `noise-100k` | instruction + ≈100k tokens 无关材料 | ~105k（192k 的 55%）|

- `clean` **不重跑**：直接复用 P0 的 80 trial 结果（同 wheel、同 profile、同 served pin），保证严格可比。
- 两档噪声是为了得到**剂量-反应曲线**：如果 `noise-30k` 无影响而 `noise-100k` 有影响，说明阈值在中间；如果两档都无影响，说明这套题确实不吃上下文。

### 2.2 因变量

- **planned 通过率**（主）、**partial**（连续量，对本实验尤其敏感）、**observed**（辅助，须标幸存者偏差）
- `strict` 口径已于 2026-11-07 废除（前提被证伪），**不得再作为因变量**
- **退化量 Δ** = clean 通过 − noise 通过（配对，按题 × repeat 对齐）
- 辅助诊断：input tokens、模型调用次数、摘要触发次数、tool 调用分布、是否出现"读了噪声文件"

### 2.3 噪声规范（关键，做错就整批无效）

必须同时满足：

1. **确定性可复现**：由 `(task_id, 档位)` 经固定 seed 生成，同一输入永远同一噪声；噪声内容的 SHA-256 记入 manifest。
2. **任务无关**：不来自该 task 的目标仓库，不包含该 task 的 issue/PR/patch 片段。
3. **不提供线索**：不含目标函数名、不含修复思路、不含测试断言。
4. **不破坏可解性**：不改文件、不改环境，只进 prompt。
5. **形态可信**：是"像真的项目背景材料"——历史设计文档、变更日志、issue 讨论串、告警日志，而不是随机字符（随机串会被模型一眼识别为噪声并忽略，测不到干扰）。

**实现方式**：从本机已有的 519 题元数据缓存里，取**其他仓库**的 README/CHANGELOG/文档原文拼接（真实、长、与目标任务无关），按 seed 抽取与截断到目标 token 数。

### 2.4 注入通道

`variant.json` 的 `instruction_append` 字段只对 SAYACODE 生效（`adapter.py:166-171` / `worker.py:894-897`）；三个基线 agent 由 Harbor 直接传 instruction，**读不到 variant**。

因此需要在 `scripts/locked_agents.py` 的四个 `run()` 里加统一注入：

```python
def _append_noise(instruction: str) -> str:
    path = os.environ.get("SAYACODE_BENCH_NOISE_FILE")
    if not path:
        return instruction
    text = Path(path).read_text(encoding="utf-8")
    return instruction + "\n\n" + text
```

- SAYACODE 走 `variant["instruction_append"]`（已验证可行），基线走上面这个钩子；**两条路的最终 instruction 必须字节一致**（用同一个噪声文件、同一个分隔符），否则组间不可比。
- 注入后 instruction 的 SHA-256 记入 manifest，用于事后核验。

### 2.5 题选择（控制样本量与成本）

从 40 题里选 **12 题**，判据：

- P0 结果里 **clean 通过**（否则没有退化空间，天花板/地板效应）；
- 覆盖至少 4 个仓库，避开 vuls 重题（内存）；
- 按「clean 下 patch 中位行数」分层（浅/中/深各 4 题）。

规模：12 题 × 2 重复 × 2 噪声档 × 4 agent = **192 trial**，单题约 4–14 分钟，并发 2 → 约 **12–16 小时**。

若时间不足，先只跑 `noise-100k` 一档：12 题 × 2 × 1 × 4 = **96 trial**，约 6–8 小时。

### 2.6 分析与判定

1. **配对 McNemar**（题 × repeat 为单位，clean vs noise，各 agent 分别做）。
2. **退化量差值**：Δ_sayacode vs Δ_baseline，用题块 bootstrap 10000 次（seed `20261022`）给 95% CI。
3. **剂量-反应**：两档噪声的 Δ 是否单调。
4. 预注册判定（写下来防止事后解释）：
   - **假设成立**：`noise-100k` 下至少一组的 Δ ≥ 15pp，且 SAYACODE 的 Δ 与其他组的最小差值 ≥ 10pp（CI 不含 0）。
   - **假设不成立**：四组 Δ 都 < 5pp 且两两不显著 → 结论是"这套题不吃上下文，必须换维度"，而不是"SAYACODE 更强/更弱"。
   - **中间地带**：只有部分组显著退化 → 报告为"上下文是区分维度之一"，不给单一排名。

## 3. 必须避免的坑

| 坑 | 后果 | 规避 |
|---|---|---|
| 噪声内容含目标任务线索 | 变相提示，结果无效 | 只取其他仓库文本 + 生成后关键词自查（目标 repo 名/函数名出现即重抽） |
| 噪声触发上下文摘要 | 测的变成"摘要能力"而非"抗干扰" | 档位定在摘要触发点（150.4k）以下，最高档 100k 留余量 |
| 只跑 SAYACODE 不跑基线 | 无法归因 | 四组同批同题 |
| clean 基线用了不同 wheel/profile | 不可比 | clean 直接复用 P0（3.2.7 + served pin） |
| instruction 长度差异导致 SDK 行为差异 | 假效应 | 注入前后都记录 instruction SHA-256 与 token 数 |
| 只报"通过率下降" | 掩盖地板效应 | 必须报 clean 基线通过率与退化幅度 |

## 4. 执行顺序（P0 之后）

1. 收 P0 结果 → 选定 12 题 → 生成两档噪声文件（含 SHA-256）。
2. 给 `locked_agents.py` 加噪声钩子 + 单测（验证 4 个 agent 的最终 instruction 一致）。
3. 单题 smoke（1 题 × noise-100k × sayacode），确认 instruction 真的变长、上下文占用上升、无摘要触发。
4. 四组 × 12 题 × 2 档跑批（分片：非 vuls 并发 2）。
5. 汇总：`planned` + `partial` 口径 + 配对退化分析（新增 `scripts/analyze_context_ab.py`）。**不要用 `strict_compare`**——其 `strict` 输出已于 2026-11-07 废除，仅保留 planned/observed 可用。

## 5. 与简历/结论的关系

- 如果假设成立：得到"在需要长上下文的条件下，SAYACODE 比基线退化更少/更多 X pp"——这是**有区分度**的结论。
- 如果假设不成立：得到"该题集的瓶颈不在上下文"，同样是有价值的负结果，且**必须放弃**用这套题做排名。
- 无论哪种，都**不得**用它反推"SAYACODE 更强"——只有配对退化量的 CI 才可引用。
