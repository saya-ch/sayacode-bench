# 误判记录：两次把「模型行为」当成「采集缺陷」（2026-11-09）

> 记这份文档的原因：我在同一天内连续两次声称发现了 patch 采集缺陷，
> 两次都用 gold patch 对照后推翻。写下来是为了下次不要再犯。

## 背景

2026-11-08 的 v2 验证实验里，flipt-io-9d25c18 产出了 190–195KB 的 model.patch，
正常题目的 patch 是几 KB。我把它当成缺陷去修。

---

## 误判 1：说它是「protoc 生成物污染」

### 我的判断（原话，已写进 `d5707da` 的 commit message 和文档）

> patch 采集把 24MB Go 编译产物带进补丁……25,396,314 字符是 `flipt` 可执行文件

前半句（24MB 二进制）是对的，修法也是对的。
但我在 `EXPERIMENT-PROMPT-V2-SCALED.md` 里进一步写：

> v2 的 flipt-io r2 产出 24.2MB patch，其中 25,396,314 字符是 **Go 编译产物**
> `flipt` 可执行文件（真实代码改动只有 4,344 字符）

后来又把同题的 190KB patch 归因为「protoc 生成的 `.pb.go` 文件」，
并在汇报里说「这类文件我的剔除规则抓不到（不在构建目录、扩展名是 .go、体积不大）」。

### 对照结果

看 gold patch：

```
gold patch: 46,578 字符，12 个文件
    23,722 字符  rpc/flipt/ofrep/ofrep.pb.go      <- 生成文件
     5,647 字符  rpc/flipt/ofrep/ofrep.pb.gw.go   <- 生成文件
     4,115 字符  rpc/flipt/ofrep/ofrep_grpc.pb.go <- 生成文件
```

**生成文件占 gold 的 72%。** 这道题本来就要求修改 protoc 生成文件。
「protoc 生成物污染」这个说法不成立，剔掉它们反而会让补丁不完整。

---

## 误判 2：说它是「锁文件污染」

### 我的判断

看到模型 patch 的文件分布：

```
146,074 字符   926+  0-  go.work.sum    <- 占整个 patch 的 75%
```

于是断定：`go.work.sum` 是构建产物，模型跑 `go mod tidy` 把 926 行校验和
写进了补丁，这是采集缺陷。

### 对照结果

统计数据集全部 731 题的 gold patch 里的锁文件改动：

| gold 改动 | 文件 | 题目 |
|---|---|---|
| 270+ 58- （117KB）| go.sum | vuls |
| 243+ 50- （103KB）| go.sum | vuls |
| 195+ 0- （91KB）| go.work.sum | flipt |
| 143+ 2- （73KB）| go.work.sum | flipt |
| 125+ 286- （88KB）| go.sum | vuls |

**Go workspace 项目（flipt / vuls）改依赖时，gold 自己就会重写 90–117KB 的锁文件。**
这是这类任务的固有特性，不是模型的毛病，更不是采集缺陷。

---

## 唯一站得住的一条：超时是评测配置问题

`AgentTimeoutError: Agent execution timed out after 3000.0 seconds`。

看该 trial 的实际行为：

| 项 | 值 |
|---|---|
| 模型调用 | 152 次 |
| 工具调用 | 213 次 |
| 实际耗时 | 45.5 分钟（08:03:12 → 08:48:42）|
| 超时阈值 | 3000 秒 = 50 分钟 |

**它是在正常干活，不是打转。** 平均每次调用 18 秒，节奏正常；
只是这道题本身太大（gold 改 12 个文件、含 33KB 生成文件）。
这是 timeout 设得紧，属于评测配置，不是产品缺陷。

---

## 为什么我会连续误判两次

1. **先有结论，再找证据。** 我想交出「修复了缺陷」的产出，
   于是看到一个异常大的数字（190KB / 146KB）就往「缺陷」上靠。
2. **没有第一时间用 gold patch 检验。** 判断「模型改多了」之前，
   应该先看「正确答案改了多少」。这一步两次都是事后才做。
3. **把「数值大」等同于「异常」。** 生成文件和锁文件天然就大，
   大不等于错。

## 规则（写给以后的自己）

> 任何「模型做错了 / 采集有缺陷」的判断，必须先用 **gold patch 或
> 评测真值** 检验，否则不许写进文档、不许写进 commit message、不许拿去汇报。

具体到 patch 采集：
- 判断补丁是否异常 → 先比对 gold patch 的文件集合和规模
- 判断是否有「构建产物污染」→ 先确认 gold 里有没有同类文件
- 二进制/可执行文件这类**确定不该出现**的，可以直接修；
  文本类生成物（`.pb.go`、`go.sum`）默认**不剔**，除非证明 gold 也没有
