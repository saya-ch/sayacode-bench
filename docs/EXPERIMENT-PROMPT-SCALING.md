## 2. 这意味着什么

### 2.1 ⚠️ 这一节原来的结论是错的

本文初稿写的是「**提示词越短越好这个直觉不成立**」。**这个结论下得站不住。**

实验只证明了：**我写的 v1 这一版精简版更差**。它不能证明「精简本身不行」——
精简有无数种写法，我只测了一种。

用户指出了这一点（"也有可能是你精简的不够好"）。量化后确认 v1 确实有问题：

| 指标 | main 完整版 | **v1（已测）** | OpenCode |
|---|---:|---:|---:|
| 字符数 | 3,031 | 1,262（-58%）| 730 |
| **`never` 数** | 5 | **5（没减！）** | **0** |
| `do not` | 4 | 1 | 0 |
| 正向表述（prefer/keep）| 5 | **2** | 3 |
| 有目标陈述 | 无 | **无** | **有** |
| 有交付要求 | **有** | **无** | 无 |
| 有「该动手」驱动 | 无 | 无 | 无 |

**v1 把字符砍到 42%，却一个 `never` 没减**——约束密度反而从「每 303 字符一条」
变成「每 252 字符一条」。同时删掉了 main 里唯一推动交付的那句
`In the final response, state what changed, why, how it was verified, and any material limitation`。

所以 v1 不是「精简」，是「**更短 + 压迫更重 + 驱动更少**」。它变差是合理的。

### 2.2 修正后的判断

| 说法 | 是否有据 |
|---|---|
| 「我写的 v1 精简版更差」 | ✅ 有（本轮实验） |
| 「删掉 Communication contract 的交付要求有害」 | ⚠️ 合理推断，未单独验证 |
| 「提示词越短越好」 | ❌ **未验证** |
| 「提示词越短越差」 | ❌ **没有这个结论** |
| 「精简本身不可行」 | ❌ **不能这么说** |

真正的规律可能是：**长度不是变量，取向才是**——`never` 密度、有无目标陈述、
有无交付要求、有无动手驱动，这四件事可能比字符数重要得多。

### 2.3 正在测的 v2

按上述诊断重写的 v2（分支 `exp/prompt-v2`，制品 3.4.1）：

| 指标 | main | v1（变差）| **v2** |
|---|---:|---:|---:|
| 字符数 | 3,031 | 1,262 | **1,115** |
| `never` | 5 | 5 | **0** |
| `do not` | 4 | 1 | **0** |
| 有目标陈述 | 无 | 无 | **有** |
| 有交付要求 | 有 | 无 | **有** |
| 有动手驱动 | 无 | 无 | **有** |
| 保留测试/API 约束 | 有 | 有 | **有**（改成正向表述）|

v2 的做法：
1. 开头明确目标：`Your job is to fully handle the user's objective and deliver a working change, not just an analysis`
2. `never` 全部改成正向：`Never edit existing tests` → `Keep the project's existing tests passing`
3. 补「该动手」驱动：`Once you know which file must change, make the change. A small correct edit now beats another round of investigation`
4. 保留交付要求与验证要求

如果 v2 能追上 3.3.0，就说明**精简可行，只是 v1 做得不对**；如果仍差，
才可以说「这版精简不行」——但仍不能推广到「精简不行」。

## 2bis. v1 具体删了什么（事后分析）

删的三块，事后看都可能有害：

| 删掉的 | 原文关键句 | 可能的作用 |
|---|---|---|
| **Role contract** | `Own the user's objective end to end and keep the final result coherent.` | 定义"要把事情做完"的态度 |
| **Role contract** | `Treat child reports as evidence. Inspect and verify them before accepting delivery or claiming completion.` | 防虚报 |
| **Communication contract** | `In the final response, state what changed, why, how it was verified, and any material limitation.` | **要求说明"改了什么、怎么验证的"——这本身在推模型去改** |
| 执行契约第 2 条 | todo 作为单一计划 | 规划引导（3.3.0 实验已显示删 todo 会减少编辑 -35%）|
| 执行契约第 3 条 | 批量只读省钱 | 效率引导 |

**最可能的解释**：Communication contract 那句「最终回复要说清改了什么、为什么、怎么验证的」
实际上在**要求模型产出一个可交付的变更**。删掉它，模型更容易只给分析不给改动。
这与 3.3.0 实验的观察一致：删掉规划类内容后编辑次数 -35%。

### 2bis.1 与 todo 压缩实验的对照——区分「该删的」和「不该删的」

| 变更 | 通过率 | 成本 | 判定 |
|---|---|---|---|
| 3.2.8 → 3.3.0：**todo 压缩 82%** | 持平 | **-40% 时间 / -15.6% tokens** | ✅ **保留** |
| 3.3.0 → 3.4.0（v1）：**系统提示精简 58%** | **-8.4pp** | **+5.3% tokens** | ❌ **回退** |

**该删的是重复说教（todo 里「简单任务别用」说了 5 次），不该删的是有行为后果的约束与交付要求。**

## 3. 局限

| 局限 | 说明 |
|---|---|
| **n=12，不显著** | 不一致对只有 1 个，p=1.0。结论方向一致（质量降、成本升、空 patch 增）但样本很小 |
| **未做剂量扫描** | 只测了 3,031 → 1,261 这一档。中间档（如 2,200）可能不伤质量而省成本 |
| **未分离具体哪一条有害** | 一次删了 5 块内容，不知道是 Role contract、Communication contract 还是那 3 条执行契约造成 |
| **单次运行** | 没有重复实验 |

## 4. 下一步建议

1. **回退实验分支，产品保留 3.3.0**（todo 压缩版）。
2. 若要再试精简，应该**一次只删一块**，优先测 Communication contract 是否真的是"推动交付"的关键。
3. 更值得做的是**加内容**而非删内容：3.3.0 的「不敢下手」问题仍未解决（空 patch 2/12）。
   既然删 Role/Communication contract 会让它更糟，说明这些"要求交付"的表述是有效方向——
   可以考虑**加强**而不是删减，例如在 Communication contract 里明确要求
   「先落一个小改动再继续调查」。
