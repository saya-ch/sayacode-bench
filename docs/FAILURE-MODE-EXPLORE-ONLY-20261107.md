## 3. 两种失效模式（都是行为问题，不是知识问题）

### 模式 A：纯探索后放弃（2 个 trial）

| trial | 工具序列特征 |
|---|---|
| **NodeBB r1** | 46 次工具 **全是** `grep_search` / `read_file` / `glob_search`，**0 次写操作**；最后 8 个动作仍是 `read_file, read_file, grep_search, grep_search` |
| **navidrome r1** | 13 次工具全是 `read_file` / `list_directory` / `grep_search`，**0 次写操作** |

**它们不是"改错了"，是"没改"**。模型研究了 46 次/13 次，然后直接结束，`model.patch` 是 0 字节。

### 模式 B：探索过久后改错（3 个 trial）

| trial | 首次编辑出现在第几个动作 | 模型调用 |
|---|---:|---:|
| flipt-io r1 | **第 29 个** | 59 |
| flipt-io r2 | **第 33 个** | 73 |
| navidrome r2 | **第 42 个** | 79 |

对照：通过的 trial 一般在前 10 个动作内就开始编辑，模型调用 12–31 次。

**这三个 trial 花了 3–4 倍预算（59–79 次调用）仍在探索，落笔时已经"看花了眼"**——上下文里塞满了 100k 噪声 + 几十次工具输出，改错位置是自然结果。

## 4. 根因判断

不是模型不会做这些题（clean 组这 6 题 **12/12 全过**），而是**长上下文下缺少"收敛"机制**：

1. **没有探索预算**：模型可以无限次只读不写。NodeBB r1 探索 46 次仍不落笔，没有任何机制打断它。
2. **没有"该动手了"的信号**：产品没有基于"已定位到目标文件"或"探索次数"的收敛提示。
3. **上下文噪声放大了犹豫**：100k 无关材料让模型更难判断"信息够不够"，于是倾向于继续读。这是恶性循环——**越读上下文越乱，越乱越不敢改**。

对照 `DEEP-ANALYSIS-20261106.md` §8.3 的记录：普通（短上下文）失败时 SAYACODE 也是"越失败越不编辑"（探索 +22%、编辑更少），但那时幅度温和；**长上下文把这个倾向放大成了 0 编辑或 40+ 次探索后才编辑**。

## 5. 可执行的改进方案（按性价比）

| # | 改动 | 触发条件 | 预期效果 | 成本 |
|---|---|---|---|---|
| **1** | **探索预算护栏**：连续 N 次（建议 12–15）只读不写时，注入一条强提醒「你已收集足够信息，现在必须开始修改；若确实缺信息，请说明缺什么」 | 连续 read/grep/glob 计数 | 直接拦截模式 A（2/5 失败） | 小，一个 middleware |
| **2** | **首次编辑延迟告警**：模型调用超过 20 次仍无写操作时，同上提醒 | 模型调用计数 | 可能救模式 B | 小，同上 |
| **3** | **空转收敛**：模型调用超过 30 次且 0 写操作 → 强制收尾（产出困难说明 + 部分 patch），而不是静默空 patch | 调用计数 | 至少不让它白跑 79 次 | 中 |
| **4** | **上下文瘦身**：探索类工具输出（grep 结果）在长上下文下更激进地落盘 + 只回摘要 | 总 input > 80k | 缓解恶性循环 | 中 |

**建议先做 1 + 2**（一个 middleware 就能覆盖），然后在同一批题上重跑 noise-100k 验证：
- 预期：空 patch 从 2/12 降到 0–1/12，Δ 从 41.7pp 收窄
- 若无效，说明失效不在"该动手没动手"，而在别处（需重新归因）
