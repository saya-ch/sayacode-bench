# 深度分析：榨干已有四组数据（2026-11-06）

> 数据：`C:\sb\analysis\dataset.json`，**391 条 trial**
> （SAYACODE 3.2.7 / 3.2.5、mini-swe、Claude Code、OpenCode，各 40 题 × 2 重复，个别缺失）
> 关键新维度：verifier 的 `output.json` 给出**每个测试的 PASSED/FAILED**，因此可算**连续的部分得分**，不再只有 0/1。

## 1. 核心发现：0/1 口径丢掉了绝大部分信息

| group | n | 0/1 通过率 | **部分得分均值** | 中位 | 部分>0 且<1 |
|---|---:|---:|---:|---:|---:|
| SAYACODE 3.2.7 | 72 | 81.9% | **97.6%** | 100% | 12 |
| SAYACODE 3.2.5 | 73 | 84.9% | **99.2%** | 100% | 11 |
| mini-swe | 77 | 87.0% | **98.5%** | 100% | 10 |
| Claude Code | 76 | 86.8% | **97.8%** | 100% | 9 |
| OpenCode | 77 | 80.5% | **94.4%** | 100% | 13 |

**所有 agent 的部分得分都在 94–99%，但 0/1 只有 80–87%。** 差距全部来自「差 1 个测试」：

```
NodeBB-4327a09d   263/264 = 99.6%
qutebrowser-fec1  243/244 = 99.6%
element-web-772d  106/107 = 99.1%
openlibrary-ba3a   93/94  = 98.9%
```

也就是说：**这些题 agent 其实基本都做对了，只是卡在最后一个断言的边角上。**
0/1 通过率把这个「99% 对」压缩成 0，于是两组的差异被放大成噪声。

## 2. 核心发现：题库已饱和

跨 5 组统计（40 题，每题材 ≥3 次观测）：

| 指标 | 值 |
|---|---|
| **饱和题**（所有组部分得分 = 1.0） | **26 / 40 = 65%** |
| 死题（所有组 = 0） | **0** |
| 中间难度 | 14 / 40 |
| 题级部分得分均值 | **97.6%** |
| 有区分度（跨组 sd > 0.02）的题 | **仅 8 / 40** |

区分度最大的题（sd 高才能拉开差距）：

| 题 | 均值 | sd |
|---|---:|---:|
| `navidrome-dfa453cc` | 60.0% | 49.0 |
| `ansible-de5858f48` | 89.0% | 25.5 |
| `openlibrary-03095f26` | 93.3% | 13.3 |
| `navidrome-812dc209` | 96.7% | 10.0 |
| `element-web-d4051600` | 97.1% | 7.0 |

**这解释了为什么四组两两配对全部不显著**：40 题里 26 题对谁都是满分，
真正能区分的只有 8 题，样本量根本不够。继续在 40 题上加重复也救不回来 —— 那是给饱和题加重复。

## 3. 核心发现：2 题是「环境性不可过」，对所有 agent 同样失败

| 题 | 失败测试 | 失败次数 |
|---|---|---|
| `qutebrowser-fec187c2` | `test_safe_display_string[url5-(unparseable URL!) http://www.арріе.com]` | **10 / 10** |
| `tutanota-51818218` | `DesktopDownloadManagerTest::downloadNative, no error` | **9 / 9** |

- qutebrowser 那题 244 个测试只挂这 1 个，是 IDN（西里尔字母同形域名）在容器里的解析行为差异；
- tutanota 那题 4 个测试里挂 1 个，是 Electron 下载管理器在无网络沙箱里的环境依赖。

**这两题不反映 agent 能力，应从对比中排除**（占题集 5%，对所有组同等扣分，会稀释区分度）。
它们的 `stable_fail` 特征也说明：**「稳定失败同一测试」是识别坏题的有效信号**。

## 4. 核心发现：同题重复本身就是噪声源

同题 r1/r2 一致性（每组）：

| group | 配对题 | 稳定通过 | 稳定失败(同集合) | **随机翻转** | 不稳定失败 |
|---|---:|---:|---:|---:|---:|
| SAYACODE 3.2.7 | 37 | 28 | 3 | **5** | 1 |
| SAYACODE 3.2.5 | 37 | 31 | 2 | **2** | 2 |
| mini-swe | 38 | 32 | 2 | **3** | 1 |
| Claude Code | 39 | 31 | 2 | **5** | 1 |
| OpenCode | 40 | 29 | 4 | **7** | 0 |

**每组有 2–7 题在两次重复间翻转**（一次过、一次不过）。之前发现的「element-web r1/r2 镜像反转」
（`772df302`、`d405160080`、`qutebrowser-c09e1439f`）就是这类。

在 40 题规模下，翻转题数（2–7）已经和任何两组之间的真实差异同量级 ——
**单次对比测到的 −2.6pp 完全可能是翻转噪声的排列组合**。

## 5. 核心发现：改得多的 patch 反而更容易过

| patch 特征 | n | 部分得分均值 |
|---|---:|---:|
| patch > 5KB | 90 | **97.4%** |
| patch ≤ 5KB | 62 | 94.1% |
| 改 ≥3 个文件 | 83 | **98.2%** |
| 改 <3 个文件 | 69 | 93.5% |

不是「改得多所以错得多」，而是**需要大改的题本身描述清晰、改对了就过**；
小改题往往是边角断言，容易差一个测试。

## 6. 对「换题库」的直接指导

1. **必须换**：65% 饱和 + 只有 8 题有区分度，40 题这套在四组对比上已经到分辨力上限。
2. **换的判据要写进选题器**：
   - 排除「所有 agent 稳定失败同一测试」的题（用本次的 `stable_fail` 检测即可，跑 2 个 agent × 2 重复就能筛出来）；
   - 优先「跨组部分得分 sd 大」的题，而不是只看 0/1；
   - 控制「部分得分 99% 但 0/1 为 0」的比例 —— 它们只贡献噪声。
3. **报告口径升级**：以后同时报 `0/1 通过率` 与 **`部分得分`**（连续），后者对小样本对比敏感得多。

## 8. 行为层：工具调用结构（391 trial 的审计）

sayacode 走 `audit.jsonl`（`tool.completed` 事件），三个基线走 ATIF-v1.7 `trajectory.json`（`steps[].tool_calls`）。

### 8.1 每 trial 平均行为量

| group | 工具调用 | 探索 | 编辑 | 执行 | 模型调用 | 输入 token |
|---|---:|---:|---:|---:|---:|---:|
| SAYACODE 3.2.7 | 49.6 | 23.9 | 8.2 | 12.9 | 33.4 | 960,348 |
| SAYACODE 3.2.5 | 48.7 | 24.9 | 8.1 | 10.7 | 33.2 | 961,560 |
| mini-swe | 57.3 | 0 | 0 | 57.3 | 58.8 | 1,711,870 |
| Claude Code | 43.0 | 10.4 | 9.7 | 22.7 | 43.0 | 1,620,979 |
| OpenCode | 30.9 | 7.8 | 7.1 | 15.2 | 31.6 | 779,131 |

**SAYACODE 3.2.7 与 3.2.5 的行为几乎逐项相同**（49.6 vs 48.7 次调用、960K vs 961K token、工具分布一致）。
这给了 3.2.6/3.2.7 三项修复「成绩没有变化」一个**机制性解释：修复没有改变 agent 的行为轨迹**，
而不是「修复了但被掩盖」。

### 8.2 探索 : 编辑比 —— SAYACODE 明显更「犹豫」

| group | 每次编辑对应的探索次数 |
|---|---:|
| **SAYACODE 3.2.7 / 3.2.5** | **2.9 / 3.1** |
| Claude Code | 1.1 |
| OpenCode | 1.1 |

SAYACODE 在编辑前平均要看 2.9 次（读文件 + grep + glob），是基线的 2.6 倍。
工具分布上 `grep_search` 占 22%、`read_file` 24%、`execute_command` 26%，而基线以 `Bash` 为主（49–53%）。

### 8.3 失败 trial 的行为特征：探索变多、编辑变少

| 组 | 失败 n | 成功 n | 工具调用（失败 vs 成功）| 编辑（失败 vs 成功）|
|---|---:|---:|---|---|
| SAYACODE 3.2.7 | 13 | 59 | 56.2 vs 46.1 | **7.5 vs 8.1** |
| SAYACODE 3.2.5 | 11 | 62 | 51.6 vs 47.1 | **7.5 vs 8.4** |
| Claude Code | 10 | 66 | 61.5 vs 41.3 | **15.4 vs 9.1** |

两种截然不同的失败模式：
- **SAYACODE：越失败越不编辑**（探索 +22%、编辑反而更少）→ 卡在理解，没落到改动上；
- **Claude Code：越失败越猛改**（编辑 +69%）→ 反复试错。

合并 5 组看，失败 trial 的探索次数 +32%（16.7 vs 12.6），是「找不到方向」的典型信号。

### 8.4 工具耗时与输出体量（sayacode 3865 次调用）

| tool | n | 耗时中位 | p95 | 输出中位 | **输出 max** |
|---|---:|---:|---:|---:|---:|
| execute_command_tool | 1005 | 332ms | **71s** | 572 | 13,089 |
| analyze_project | 22 | 202ms | 1.6s | 6,976 | 19,373 |
| glob_search | 214 | 108ms | 9.6s | 41 | 5,055 |
| grep_search | 862 | 57ms | 3.8s | 147 | **125,622** |
| read_file | 909 | 18ms | 79ms | 2,988 | 23,763 |
| search_replace | 545 | 9ms | 54ms | 66 | 103 |

两处风险：
1. **`grep_search` 单次输出最高 12.5 万字符**（约 3–4 万 token），一次就能吃掉大半上下文 ——
   这正好接上 3.2.6 修的「摘要失败降级」，说明**触发摘要的路径是真实存在的**；
2. **`execute_command_tool` p95 达 71 秒**（最长 418 秒），长命令是 agent 时间的主要消耗。

### 8.5 观测盲区：工具失败没有被记录

3865 次 `tool.completed` 里，**`error_type` 全部为 `null`，没有任何一次工具失败被记录**。
这意味着：
- 无法从审计数据判断「命令返回非零 / 文件不存在 / patch 失败」等失败率；
- 8.3 的「失败 trial」只反映 verifier 结果，不反映过程受阻情况。

**这是产品侧应修的一项观测缺陷**（工具执行异常应写入 `error_type`），否则后续任何行为分析都缺一半。

### 8.6 成本

只有 ATIF 基线带 `cost_usd`：Claude Code 每 trial **$2.27**（中位 $1.19），77 trial 合计 **$174.61**。
SAYACODE 走本地网关，无计价字段，只能用 token 量对比（960K/ trial，是 Claude Code 的 59%、mini-swe 的 56%）。

## 10. 最关键的一条：这批题**从未触发过上下文摘要**

profile 是 `context_length=192000`、`summary_trigger_ratio=0.8` → 摘要触发线约 **153,600 tokens**。
统计每个 trial 的**单次调用 input_tokens 峰值**：

| 组 | trial | 峰值中位 | 峰值均值 | 峰值最大 | 超过 153.6k 的 trial |
|---|---:|---:|---:|---:|---:|
| SAYACODE 3.2.7 | 77 | 32,920 | 34,907 | 102,034 | **0** |
| SAYACODE 3.2.5 | 79 | 30,180 | 35,677 | 127,369 | **0** |

只有 1–2 个 trial 越过 100k，**没有一个到达触发线**。`events.jsonl` 里也确实没有任何
摘要 / 上下文压缩事件。

这意味着：

1. **3.2.6 修的「摘要失败降级」（`c5d2973`）在这 40 题上从未被触发** ——
   它「没有效果」不是因为它修得不对，而是因为**题集根本没有走到那条路径**；
2. 结合 §8.1（3.2.7 与 3.2.5 的行为轨迹逐项相同），3.2.7 成绩不变是**必然结果**，
   而不是「修复被掩盖」；
3. **要检验摘要相关修复，必须换成上下文能突破 150k 的任务**（长轨迹、大仓库、长测试输出）。
   现有 40 题即使加重复、加样本量，也永远测不到这条路径。

这一条把「换题库」从「分数不够看」升级成了「**测不到被测特性**」：题集与产品改动的
作用面不重叠，再跑多少遍都没有信息增益。

同理，若要检验另外两项修复（提示与工具集一致性 `60ca2f0`、CompletionGuard 判据收紧 `41b1e38`），
需要**专门构造会走到这两条路径的场景**，而不是期望通用题集自动覆盖。
