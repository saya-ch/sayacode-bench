## 四、五类缺陷

### 4.1 方法论层（36 条，其中 5 条属 P0）

**P0-1｜`strict` 口径的前提被证伪（最严重）**

`PROTOCOL-V2 §5.1`、`TEST-EDIT-ANALYSIS`、`strict_compare.py:3-5`、`STATUS.md:22` 均断言 verifier **不重置** `__snapshots__`。实测：

```bash
# 642/642 个 test.sh 的第 97-105 行
git diff --name-only HEAD -- > /tmp/v6_modified.txt
while read -r p; do
  case "$p" in
    *testdata/*|*test_data/*|*fixtures/*|*fixture/*|*mocks/*|*mock/*|*__snapshots__/*)
      echo "$p" | grep -qE '(__NONE__)' && continue
      git checkout HEAD -- "$p" 2>/dev/null || true ;;
  esac
done < /tmp/v6_modified.txt
```

- 命中 `__snapshots__/*` 的路径**一律** `git checkout HEAD`。
- `continue` 分支要求路径含字符串 `__NONE__` —— 任何真实路径都不含，**永不触发**。
- 独立复核：642 个 Pro V2 `test.sh` 全部含该分支，636 个含哨兵，642 个含 `git checkout`。

**后果**：`strict` 列（80.0 / 73.8 / 67.5 / 76.2）全部无效；"snap pass 4/3/6 个"、"OpenCode 被拖累 7.5pp"、"SAYACODE 更干净"三个叙事作废。更硬的一刀：被扣分的 mini-swe `element-web-9bf77963ee-r1` 改的两个 `.snap`，正是官方 `test_patch.patch` 要更新的路径 —— agent 的修改先被还原、再被官方补丁覆盖，与它的通过**没有任何关系**。

**P0-2｜四组正式表混用两个批次**

SAYACODE 行来自 `v4-327`（11-06，3.2.7，零 `hy3-x`，并发 4/1），三基线来自 `v2-325`（11-02~11-04，约 14.3% `hy3-x`，并发 2–4，网络修复状态不同）。`STATUS.md:24` 自己承认"只可做描述性对照"，但同文件 `:7` 仍以"四组对照"陈述结论，`:46-48` 给出三行跨批次 McNemar。**且这三行的数字经复算无法重现**（common 写 40 vs 实测 38/39；Claude 行 b_only 5 vs 文档 6；OpenCode 行 p=0.791 vs 实测 1.0）。

**P0-3｜`timeout` 是声明了但代码永远返回不到的分类**

`formal.py:35` 的 `MISSING_CLASSES` 含 `timeout`，但 `classify_missing`（`:464-476`）没有 timeout 分支。后果有方向性：超时且 `patch=0` → `empty_patch`（不补，合规）；**超时且有部分 patch → `unverified`（协议规定可补）**。即"越接近完成的超时越会被补跑"，正是 `PROTOCOL-V2 §6` 要防的选择性补偿。

**P0-4｜开发集当正式成绩，且偏置方向对被测对象有利**

40 题在 `README.md:41`、`AGENTS.md:20` 被定义为开发迭代集；`protocol.md:157` 明确禁止把开发期数字当正式成绩。SAYACODE 的提示词规则 R1–R5 正是从这 40 题的失败个案调出。`RETROSPECTIVE §5.1` 承认了这一点，但 `FORMAL-RESULTS-20261105-v3.md:136` 的"可写进简历的口径"仍直接写 78.8%，没有附偏置声明。

**P0-5｜同一批数据在多工具间不一致，且陈旧产物未重生成**

- `claude-code` passes：`FINAL-SUMMARY-V4.json` = 62，`dataset.json`（`partial==1.0`）= **65**。
- `mini-swe` missing：`STRICT-COMPARE.json` = **2**，`FINAL-SUMMARY-V4.json` = 1。
- `mini-swe` `touches_snap`：`dataset.json` = **0**，`strict_compare` `snap_passes` = 4。

## 五、根本原因分析

不是"犯了几个错"，而是**五个结构性机制**在稳定地生产错误。按危害排序：

### 5.1 口径先于证据（最根本）

`strict` 口径的诞生过程是：**想要一个"更严格"的排名口径 → 假设 verifier 不重置快照 → 据此扣除**。没有人先去读 `test.sh` 第 97-105 行。

这是**目标倒推证据**的典型形态。它在方法论上的错误是：把"我们希望的判定规则"当成了"系统的实际行为"。验证成本极低（读一个 234 行的 shell 脚本），但从未做过。

**同类模式还有**：`330 题` 的功效数字（无人推导却被反复引用）、"hy3-x 不构成混杂"（未检验池间限流）。

### 5.2 协议与执行分离

`PROTOCOL-V2` 写得非常完备：三口径、缺失七分类、worst/best 界、补跑纪律、冻结签收流程（`lock_candidate` / `validate_candidate_receipt`）。

**但按协议自己的定义，这些条款绝大多数没有执行**：

| 协议条款 | 是否执行 | 证据 |
|---|---|---|
| §7 冻结签收（`lock_candidate`） | **从未执行** | `results/` 下只有 1 个 calibration；全仓无任何 receipt 产物 |
| §4 worst/best 界 | 工具输出了，**报告没写** | `FINAL-SUMMARY-327.json` 有 `worst_bound`/`best_bound`，`FORMAL-RESULTS-20261106-327.md` 无此列 |
| §6 补跑前后同表 | v3 做了，**327 没做** | 327 无补跑，但应写"无补跑"而非省略 |
| §5.1 主报 planned | **未遵守** | `STATUS.md:7` 用 strict 名次下结论 |
| §5 题级 McNemar | 做了 | 可复算，正确 |

**后果**：`PROTOCOL-V2 §1` 明文写着"v2 的 78.8% / 70.0% / 68.8% 都是开发期诊断，不得写成对外正式成绩"。**按这句话，本项目至今没有任何一条"对外正式成绩"** —— 但 `FORMAL-RESULTS-20261105-v3.md:136` 已经给出了"可写进简历的口径"。

### 5.3 工具不唯一，产物不重生成

同一个指标有 3–4 个工具在算（`formal.py` / `final_summary.py` / `strict_compare.py` / `build_analysis_dataset.py`），各自有独立的缺失判定逻辑。结果是：

- 同一批数据，claude passes 62 vs 65；
- mini-swe missing 1 vs 2；
- mini-swe `touches_snap` 0 vs 4。

更麻烦的是**修了代码但不重跑产物**：`RETROSPECTIVE §5.7` 记录了 2026-11-05 的修复，声称"两工具完全一致"，但 `STRICT-COMPARE.json` 的磁盘时间戳是 11-05 17:23，**早于**修复声明 11-06 14:12。这意味着后续所有引用 "STRICT-COMPARE" 的数字都建立在旧文件上。

### 5.4 选题没有前置质量门

40 题是开发迭代集，其构成（饱和 65%、只有 8 题有区分度、2–3 题环境性不可过）是**跑完 4 批之后**才发现的。

SWE-EVO 接入后加了基线验证（这是正确的一步），但**又引入了新的选择偏差**：

- `swe-evo-baseline.json` 只有 **4 条** `usable`，全部是 dvc **1–2 文件 / 2–21 行**的小改动题；
- pilot 的第 5 题（dask 2022.9.2，50 文件/1525 行）是 `--include` 强制纳入的；
- 实测：4 个小 dvc 题 5/8 通过，唯一的重题 **0/2**。

**机制**：大改动题的 p2p 数量多（dask 那题 2861 个）、镜像大，因此基线验证失败的概率更高 → 被判 `broken`/`fake` 剔除 → **usable 集系统性偏向小题**。

**后果**：pilot 的 50% **不能**支撑"新题库更难"这个结论；它实际说明的是"能通过基线验证的题，大多是小改动题"。若照此扩到 20 题，结果会系统性偏乐观，且与旧题集不可比。而 `PILOT-SWE-EVO-20261106.md:82` 只写了"5 题样本太小"，**没有指出这个机制**。

### 5.5 验证成本被系统性低估

多个环节的验证成本其实极低，但被跳过了：

| 本该做的验证 | 实际成本 | 是否做过 |
|---|---|---|
| 读一遍 `test.sh` 确认快照行为 | 读 1 个文件 | ❌（导致 strict 整列作废） |
| 检查 `classify_missing` 是否有 timeout 分支 | 读 1 个函数 | ❌（导致超时被补跑） |
| 用 `git diff` 确认 3.2.7 含哪些修复 | 1 条命令 | ❌（导致报告事实错误） |
| 重跑一次 `strict_compare` 确认产物更新 | 1 条命令 | ❌（导致引用旧数字） |
| 检查 `pick_pilot.py` 的选题排序是否合理 | 读 40 行 | ❌（该脚本已成孤儿，实际 pilot 用的是另一套逻辑） |

共同点：**这些都是"读一下就能确认"的事，但都因为"结论已经符合预期"而没有去读。**

## 六、可迁移的教训

把上面五条机制翻译成可复用的规则：

1. **任何判定口径必须先在一个真实样本上验证物理行为，再定义。** 尤其当口径的名字暗示"更严格"时 —— 那是最容易倒推证据的地方。
2. **协议的所有条款都要有执行记录，没有记录就等于没有这条款。** 建议把"无记录 = 未执行"写进协议本身。
3. **同一事实只允许一个工具计算、一个文件存储。** 现在四组数字在 7 处维护，必然漂移。
4. **修了代码必须重跑产物，并在产物里写入生成时间与代码版本。** 否则"已修"是假的。
5. **新题库准入必须同时做两件事：合法性验证（有假题吗）+ 难度/区分度预检（能拉开差距吗）。** 只做前者会引入"小题偏差"。
6. **修复的证据强度必须分级，且"代码改好了"不算证据。** 本次 11 项产品修复中有 7 项停在这个等级。
7. **不要用跨批次的 p 值。** 批次效应无法通过统计手段剥离。
8. **"未检出差异"和"无差异"是两句话。** 前者需要功效分析才能升级为后者。
