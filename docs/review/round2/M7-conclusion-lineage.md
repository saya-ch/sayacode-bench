> 通道：第二轮复盘 M7。**只读审计，未修改任何现有文档**；本文件是唯一新增产物。

## 0. 一句话

这批工作的错误不是随机失误，而是**九种可复现的机制**在稳定产出错误；其中**最致命的三种**是「目标倒推证据」「文档自述当事实」「工具不唯一」；而且**大多数错误是靠外部触发（换题库、换基线、复盘、用户质疑）才暴露的，不是靠自检**——发现延迟的中位数约 1 天，最长的 `strict` 拖了 3.8 天、Codex 组拖了 4 天，代价分别是「一整列数字作废」和「240 trial 作废 + 换基线重跑」。

## 2. 认知失败模式归类（9 类）

> 按**根因机制**分类（不是按表面症状）。「出现次数」= 在 §1 的 17 条中对应条数（一条可计入多类）。
> 「机制防错」必须是**检查项 / 断言 / 工具**，不是「注意点」。

### M1 目标倒推证据（想要某个口径/结论 → 假设系统行为 → 不读实现）

- **出现次数**：3（L9 strict、L12 330 题、L10 四组可排名）。
- **最典型**：L9——「想要一个更严格的排名口径 → 假设 verifier 不重置快照 → 据此扣除」；`test.sh` 第 97-105 行与已读的 38/43 行在**同一个 234 行文件**里，却从未打开。R1 复盘的原话：「这是目标倒推证据的典型形态」。
- **机制防错**：
  1. **口径定义必须附「行为实测」**：每个口径（planned/observed/partial/任何新口径）在 `docs/PROTOCOL-V2.md` 抬头登记「验证该口径的实测证据文件:行号」，无证据不得写入 §2。
  2. 建 **`scripts/probe_verifier_behavior.py`**：对 N≥5 个不同模板的 `test.sh` 断言「重置路径集合」，输出 JSON 存 `docs/review/evidence/`；CI 在 `docs/**` 含「verifier 行为」类断言时强制读取该 JSON。
  3. 发布前跑「反向检查」：把口径的名字删掉，问「如果这个口径叫 X，证据是什么」——答不出即拒绝。

### M2 文档自述当事实（引用「已修 / 已对齐 / 已验证」而不复算）

- **出现次数**：4（L17 「已对齐」、L2 的「已修正」链条、L18 的「无效果」表述、以及第一轮复盘自身对「archive v1 报告 0 字节」的误述）。
- **最典型**：L17——`RETROSPECTIVE-20261105 §5.7` 声称「两工具完全一致」，但 `STRICT-COMPARE.json` 的 mtime 早于修复声明。**第二轮复盘也犯了同类错误**：R1 数据层写「`docs/archive/FORMAL-RESULTS-20261031.md` 是 0 字节空文件」，实测该文件在 git 中为 **3725B（`0c2ac79`）/ 4333B（`d689f80`）**，非空。
- **机制防错**：
  1. 所有汇总产物写 **`generated_at` + `script_sha256` + `data_root_mtime`**；引用方脚本断言 `generated_at > 修复 commit 时间`，否则报「stale artifact」。
  2. 文档里「已修/已对齐」必须带**可复算命令**（`git show <commit>:<file> | ...`），没有命令的「已修」一律视为未验证。
  3. 复盘/评审文档本身也要过同一个检查：引用他人结论时附 `文件:行号`，评审方抽查 ≥3 条。

### M3 跨批次混用（拿不同时期的数字拼一张表）

- **出现次数**：4（L10 四组、L1 三套分母、L2 两套口径、L12 跨仓数字）。
- **最典型**：L10——四组表里 SAYACODE 来自 v4-327（3.2.7、零 hy3-x），三基线来自 v2-325（3.2.5 期、14.3% hy3-x），却给了跨批次 McNemar 三行；R1 复核这些 p 值「无法重现」。
- **机制防错**：
  1. 结果表**第一列强制 `batch_id`**（如 `v2-325` / `v4-327`），同一行只能有一个 `batch_id`；CI 检查「同表出现 >1 个 batch_id 时禁止输出排名/p 值」。
  2. 跨批次对比只允许做**配对同题差**（同一任务两次运行），且必须标「跨批次，不参与排名」。
  3. 报告模板（`docs/REPORT-TEMPLATE.md`）加字段 `batch_ids: []`，为空或缺批次号的表格直接判不合格。

### M4 工具不唯一 / 产物不重生成（同一指标 3–4 个实现）

- **出现次数**：4（L17、L1 的分母、L2 的口径、以及 R1 数据层的「claude passes 62 vs 65、mini missing 2 vs 1、touches_snap 0 vs 4」）。
- **最典型**：同一批 trial，`FINAL-SUMMARY-V4.json` 的 claude passes=62，`dataset.json`（`partial==1.0`）=65；`STRICT-COMPARE.json` 的 mini missing=2，`FINAL-SUMMARY` =1——**没有一方是「唯一真相」**。
- **机制防错**：
  1. **单一计算入口**：结果只由 `formal.py` 的 `Trial` 语义产出；`strict_compare.py`、`build_analysis_dataset.py` 等只允许**读同一个汇总 JSON**，不得各自重算 missing/observed。
  2. CI 加 **`scripts/reconcile_results.py` 对账 gate**：同一批数据两个工具的输出 diff 必须为空，否则构建失败（`reconcile_results.py` 已存在，但未进 CI）。
  3. 删掉其余计算路径（或在文件头标「deprecated, 仅调试」）。

### M5 相关性当因果（patch 特征 → 通过；行为特征 → 能力）

- **出现次数**：4（L2 的「含 `.snap` → 靠它通过」、L14「部分得分高 → 基本做对」、DEEP-ANALYSIS §5「patch 大 → 更容易过」、§8.2「探索:编辑比 2.9 → 更犹豫」）。
- **最典型**：L2/L9——mini-swe `element-web-9bf77963ee-r1` 的 patch 含两个 `.snap` 且 reward=1，于是被推断为「靠改快照通过」；实际上这两个 `.snap` 正是**官方 `test_patch.patch` 要更新的路径**，agent 的修改先被还原、再被官方补丁覆盖，与通过无因果关系（R1 §四.1）。
- **机制防错**：
  1. 结论字段加 **`causal_evidence: none | mechanism | ab`**；`none` 时禁止写「导致/靠…通过/因为…所以」。
  2. 对「行为 → 结果」的推断，要求给出**机制证据**（如 verifier 实际读取的是哪个版本的文件）或**对照实验**（开关某一行为）。
  3. 报告模板加「机制说明」一栏，空着就降级为 B 类（描述性）。

### M6 选择偏差（幸存者 / usable 偏差 / observed 当 planned）

- **出现次数**：3（L14 的部分得分只算有输出 trial、L19 的 usable 集偏小、以及 observed 84.8% 被当 planned 的反例）。
- **最典型**：L19——SWE-EVO 的 `swe-evo-baseline.json` 只有 4 条 usable，全部是 1–2 文件 / 2–21 行的小改动题；大改动题 p2p 多、镜像大 → 基线验证更易失败 → 被剔除 → **usable 集系统性偏向小题**；pilot 50% 因此不能支撑「新题库更难」。
- **机制防错**：
  1. 新题库报告强制附**纳入/排除清单**与「排除原因 × 规模」分布表（文件数/行数分档）。
  2. 抽样按 gold 改动量分层（1–2 / 3–5 / 6–10 / 11+ 各取若干），**不得用 usable 全集**。
  3. 任何率值必须同时给 `planned` 与 `observed`，并标「observed 有幸存者偏差」。

### M7 未验证数字被反复引用（数字一旦写出就获得「事实」地位）

- **出现次数**：5（L12 330 题、1.43M tokens/任务、CI ±12pp vs ±14.8pp、题集中位 2 文件/64 行 vs 3 文件/70 行、饱和题 26 vs 28）。
- **最典型**：L12——「330 题」从产品仓一份 10-29 的功效表（那里有推导：80% power、α=0.05、10pp→330）被引用到 bench 的 completion-guard 报告，再引用到 v3，**推导在跨仓引用中丢失**，最终被复盘判为「全仓库没有这个数字的推导」。同理「1.43M tokens/任务」未标 agent，而 DEEP-ANALYSIS 显示四组 token 在 **779K–1.71M** 之间。
- **机制防错**：
  1. 数字必须带 **`source: <path>#<line>` 或 `derivation: <script>`**；CI 用 lint（`scripts/lint_metrics.py`）匹配「无来源的数字」并报错。
  2. 跨仓数字必须写**绝对路径**（如 `C:\develop\sayacode\docs\evaluation\...`），禁止只写相对名。
  3. 同一事实只允许一个文件维护（见 §4 单一真相源）。

### M8 单点证据外推（n=1 / n=10 被当成机制或趋势）

- **出现次数**：5（L6 OpenCode 自家模型、L15 task_count、L19 pilot 50%、静态预测 60%、摘要修复单题 1.0）。
- **最典型**：L19 的 pilot 50% 是 **n=10**（5 题 × 2），R1 明确判为 B 类；静态预测 60% 也是 n=10，CI 约 ±30pp，写「≈随机」本身是过度解读。
- **机制防错**：
  1. 报告模板对 `n < 20` 的结果**自动加横幅**「方向性，不构成统计结论」；`n < 10` 时禁止出现「证明/成立/说明」。
  2. 任何「机制收益」结论必须给 `mechanism_triggered: true/false`（如 `task_count>0`、摘要事件出现），未触发时写「未测到」而不是「无收益」。
  3. 单点证据只允许进「假设池」，不允许进结论账本 A 类。

### M9 验证成本被系统性低估（读一下就能确认的事，因为「结论符合预期」而没读）

- **出现次数**：4（L9 读 `test.sh`、L11 `git diff`、L17 重跑产物、L4 轨迹审计）。
- **最典型**：R1 §5.5 列出的 5 件事——读 `test.sh`（1 个文件）、检查 `classify_missing`（1 个函数）、`git diff`（1 条命令）、重跑 `strict_compare`（1 条命令）、检查选题脚本（40 行）——**全部没做**，因为结论已经「看起来对」。
- **机制防错**：
  1. 发布前 checklist 增加「**读实现**」硬项：每个结论必须附「已读 `文件:行号`」，且由第二人抽查。
  2. 每个口径/数字要求 **1 条可复现命令**；`docs/review/` 里存命令与输出片段。
  3. 「一次跑通」不算验证：口径类断言要求 **≥3 个不同模板**的样本（如 642 个 `test.sh` 里抽 5 个 flipt/openlibrary 模板）。

### 附：M10 身份/归因错位（可并入 M2/M8，但值得单列）

## 3. 发现延迟与代价的关系

### 3.1 延迟分布（n=17）

| 延迟 | 条数 | 条目 | 触发源 |
|---|---:|---|---|
| 分钟级（≤10 分钟）| 3 | L5（1 分钟）、L16（4 分钟）、L19（3 小时*）| **自检**（作者当天重看一条命令/一个假设）|
| 小时级（1–12 小时）| 4 | L6（10h）、L11（7h）、L18（7h）、L19（3h）| 外部触发（换基线/复盘）与自检混合 |
| 天级（1–4 天）| 9 | L1、L2、L3、L4、L7、L9、L10、L12、L13、L15、L17 | **外部触发**为主：换题库、换基线、第一轮复盘、用户质疑 |

*L19 从 18:44 到 21:28，约 3 小时。

### 3.2 关键数字

- **中位延迟约 1 天**；最长 **3.8 天（L9 strict）** 与 **4 天（L4 Codex）**。
- **发现方式**：17 条中约 **11 条靠外部触发**（换基线、换题库、复盘、用户质疑、跨仓核对），**6 条靠自检**（且自检的 6 条中 4 条在小时级以内）。
- **代价与延迟正相关**：
  - L4（4 天）→ Codex 组 160 trial 作废 + 换基线重跑 80 trial；
  - L9（3.8 天）→ strict 整列作废 + 3 个叙事 + 第一轮全面复盘（约半天人力 + 多文档返工）；
  - L1（1 天）→ 240 trial 重跑（约 2 天机时）；
  - L5/L16（分钟级）→ 几乎零成本（改几行文档）。

### 3.3 这个规律说明什么

**自检的边界是「当前上下文窗口」**。分钟级发现的错误（L5、L16、L8）都有一个共同点：**推翻它只需要在同一份材料里多读几十行 / 多跑一条命令**——也就是「证据就在手边」。而天级错误的共同点是：**证据在另一个文件/另一个批次/另一套工具里**，只有外部事件（换题库、换基线、复盘）才强制人去看。

所以「多数错误靠外部触发」不是偶然，而是**流程里没有内建外部触发**：发布前没有人被迫读 `test.sh`、没有人被迫跑 `git diff`、没有人被迫重跑产物。**外部触发之所以有效，是因为它换了一个证据面**。

**推论（写进机制建议）**：不要指望「下次更仔细」；要把外部触发**内建成发布前仪式**——每份结论发布前强制做一次「换证据面」的动作（读实现 / 重算一遍 / 用第二个工具对账 / 让第二人复述）。

## 5. 结论发布前硬性检查清单（10 条，可勾选）

> 用法：任何结论（数字、排名、因果、成本、难度）进入对外文档前逐条勾选；任一条不满足 → 降级为 B 类（描述性）或删除。

- [ ] **1. 证据可追**：每个数字都能对应一条命令 / 一个原始 JSON / 一次实验，且写出 `文件:行号` 或脚本路径；无来源的数字不得出现。（违反检测：`lint_metrics.py` 匹配无引用数字）
- [ ] **2. 分母一致**：所有通过率同时给 `planned` 与 `observed`（observed 标幸存者偏差），并给缺失分类与 worst/best；缺一列即不合格。
- [ ] **3. 批次单一**：结果表每行只有一个 `batch_id`（批次 + 制品 + served 池）；同一张表出现跨批次时，禁止排名与跨批次 p 值。
- [ ] **4. 口径先验证**：任何新口径/新指标先附「实现行为实测」（如 `test.sh:97-105` 的 JSON 探针），再写入协议；无实测不得定义。
- [ ] **5. 已修必复算**：「已修 / 已对齐 / 已验证」必须附重跑产物路径 + `generated_at`，且 `generated_at >` 修复 commit 时间；否则写「待复算」。
- [ ] **6. 工具唯一**：同一指标的多个计算工具必须通过对账 gate（同批数据 diff 为空）；否则只允许一个入口，其余标 deprecated。
- [ ] **7. 因果有机制**：「A 导致 B / 靠 A 通过」必须给机制证据（verifier 读哪版文件、哪条代码路径）或对照实验；只给相关性时必须写「相关性，未验证因果」。
